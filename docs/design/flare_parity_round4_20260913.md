# Fourth iteration: allocator reuse and snapshot-history capacity

The shared path remains Prepare window row -> task slice/optional negatives -> graph accessor -> Batch -> dependency access -> model -> task -> state/cache update. No numerical operator, target owner, sampling, compensation formula, optimizer or collective schedule changes. The existing internal model scan conventions still remain; this does not complete the minimal model-interface migration.

## Two changes and their evidence

1. The common DataLoader reuses its dedicated CUDA prefetch stream per StoreBundle/device through the existing GraphStore.runtime_cache. Queues, readiness events, record_stream and joined workers are unchanged. No stream is shared with CommScheduler. The old implementation allocated a new stream each epoch. In a real Flickr h8 ten-epoch diagnostic, rank1 end allocated remained exactly1,980,835,840 bytes for both versions while end reserved changed from35,100,033,024 to9,007,267,840 bytes. This is observed allocator capacity reuse, not a claim of a growing live tensor leak or an infinite-epoch bound. No empty_cache was inserted. Distinct store/device streams remain separate; concurrent mutable-store training is not a newly supported mode.

2. Coupled snapshot history builds its exact node union with a CPU bool membership array and tensor index_fill_/nonzero, then copies only sorted unique IDs to GPU. The loop is once per prepared snapshot at construction, never per node or training update. IDs, subscriber request ordering, packet layout, W+1 slots and increment/gamma math are unchanged. In a synthetic real-constructor test with N=1e6, U=600k, W8,h8,T=8/64/128, the old node ID logical size stayed4.8MB but storage was40.4/309.2/616.4MB. New storage was4.8MB in every case. AtT128 allocator peak fell1,889,660,416 ->434,000,896 bytes and retained allocated fell1,043,600,896 ->432,000,512 bytes. Constructor time increased0.0897 ->0.1272s: this is a memory optimization. This particular GPU unique result retained excess storage in this installed environment; no blanket claim about all Torch versions.

## Alternatives and limits

Reuse Torch streams and the current cache, with no new stream manager, loader or public knob. Torch CPU tensor membership removes both simultaneous all-snapshot H2D inputs and the oversized retained unique storage. DGL/custom CUDA cannot remove an avoidable transfer/lifetime; no native kernel was added. A cloned GPU unique result could compact retained storage but would still require the original all-snapshot temporary peak. Prefix views were screened (39 CPU passes) without a measured timing improvement and remain unintegrated; fixed-dst transfer was only CPU-screened and remains unintegrated.

Flickr source is soc-flickr-growth, N=2,302,925,T=70, fixed Flare partition/W8/F2/J128/s=.1. Independent default-SG h64 completes3epochs; rank1 peak allocated24.654GiB and final reserved43.322GiB. h128 fails with CUDA OOM on rank1 during the first epoch (GCN/GRU candidate concatenation); there is no completed h128 curve. Both activation capacity and allocation fragmentation remain possible contributors; no single cause is claimed. These are model-width capacity diagnostics, not larger-N experiments or native-Flare convergence measurements.

Full-time feature/task GPU tables, full-domain row maps, and node/rank imbalance remain scale risks. Larger raw datasets are present but matched four-rank larger-dataset Prepare/whole training is not validated. Main source integration, fresh paired clean performance/gradient audit, and final regressions follow in the migration log.
