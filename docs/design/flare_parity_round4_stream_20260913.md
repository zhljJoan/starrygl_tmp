# Fourth iteration: reuse loader CUDA stream across epochs

Common path before editing: Prepare window row -> DataLoader/accessor -> prepared task/optional negatives -> graph -> Batch -> dependency access -> model -> loss -> runtime state/cache update. The existing DataLoader orchestrates Event/Snapshot and node/edge alike. Only its existing prefetch stream lifetime changes, not queues, routes, waits, communication epochs, or any model math.

Real Flickr hidden8/W8 ten-epoch capacity run: rank1 end allocated=1,980,835,840 bytes remains constant while reserved reaches35,100,033,024 bytes, growing ~2.9GB in the final epoch. Each run_epoch creates a new DataLoader and thus torch.cuda.Stream. Hypothesis: per-stream allocator free lists cannot reuse the previous epoch's stream allocations; we will test the hypothesis using a single store/device stream instead of assuming a Tensor leak. Random shape variation remains another possible contributor.

Reuse one existing CUDA prefetch stream in GraphStore.runtime_cache keyed by resolved device; reuse the stream only, never rows/Batches/tensors/state. CPU paths allocate none. Each loader still waits on its current compute stream and uses its own ready events and joins source/stage workers on exit. Distinct stores/devices get separate streams. Concurrent consumers of one mutable StoreBundle were not a supported training mode; sharing a CUDA stream merely orders launches and does not relax any dependency. No stream is shared with CommScheduler.

Alternatives: torch CUDA streams and existing GraphStore runtime_cache suffice; DGL or new native kernels cannot fix allocator lifetime. No new public API/config or helper abstraction. Verify GPU stream identity/device switching and two-epoch model/gradient behavior; repeat ten-epoch memory diagnostic without empty_cache and clean timing before integration. Residual concerns: reserved may still grow with shapes; live feature/task/history bytes still scale with data.
